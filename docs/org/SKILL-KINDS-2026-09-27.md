# Skill kinds — approved 2026-09-27 (CEO), rollout owned by the COO

The CEO defined three kinds and approved four more proposed by the CTO ("เห็นด้วยทั้ง 7 หมวดหมู่").
Each org skill has ONE primary kind, chosen by the test question.

| Kind | What it is | Test question |
|---|---|---|
| **Rules** | The org's binding rules only; no outside knowledge; changes only by a CEO ruling | Is breaking it a violation? |
| **Knowledge** | Facts about outside systems read or measured at the source (they expire: carry a `verified:` date) and lessons learned from mistakes (Field notes) | Can it turn false when the outside world changes? |
| **Workflow** | One project end to end, start to public release; points to the skills that own each step, holds no rules | Does it start from nothing and end at a public release? |
| **Procedure** | One bounded task, input → one output, usually with a script | Can it be done in one sitting for one deliverable? |
| **Standard** | What a good deliverable looks like; used to write and to check | Does it define what good output looks like? |
| **Gate** | A check before a risky step; ends in pass / fail and refuses on fail | Does it end in pass / fail? |
| **Protocol** | How the org itself runs: sessions, terminals, spawning workers, logins, skills, role playbooks | Is it about running the org rather than the work? |

## Where the kind lives (the CTO's proposal the CEO accepted)

Not in memory: memory is per machine and read only by C-level sessions; workers and other machines never
see it. Four layers that travel with the repo:
1. `kind:` in each skill's frontmatter, and the kind word first in the description (`RULES — …`): every agent
   already sees the skill list with descriptions at session start, on every machine.
2. A `skill-lint` code at commit: an org skill without a valid kind is refused; imported skills are exempt.
   **Done 2026-09-28 (CEO "Ok ลุย")** — `scripts/skill-lint.py` codes 11–16 (kind, name, owner, description
   prefix, expired stubs, stale index), lists in `config/skill-kinds.yaml`. It *reports* rather than refuses:
   skill-lint stays a lint, never a gate (ADR 0022 decisions 4 and 10); the pre-commit hook prints it.
3. A reminder hook when a `SKILL.md` is written: shows the create / update procedure at the moment it applies.
   **Done 2026-09-28** — `scripts/hook-skill-write-reminder.py`, PostToolUse `Edit|Write|MultiEdit` in
   `.claude/settings.json`: §4 / §5, the Field-note line, the commit prefix, the index, that skill's lint findings.
4. An index grouped by kind, generated by `skill-curator`.
   **Done 2026-09-28** — `python scripts/skill-curator.py index` writes `docs/org/SKILL-INDEX.md`; lint code 16
   reports a stale copy.

## The create / update procedure (to land in `skill-author`)

**Create:** (1) search for an owner first; update it instead of making a second one · (2) pick one kind by the
test; content spanning two kinds is two skills · (3) name by the convention (`<ROLE>_<Engine>_<Topic>`; the
kind-in-name migration is a separate plan) · (4) scaffold with `skill-curator.py create`, never in
`~/.claude/skills` · (5) body from the kind's template (Rules: Why hard; Knowledge: source, date,
refresh_after; Workflow: gate + owner pointer per step; Procedure: input, output, script; Gate: pass / fail
output) · (6) description starts with the kind, ≤350 characters, triggers taken from the CEO's own phrases ·
(7) lint passes and every path it names exists · (8) commit `skill(<name>): new — …` and tell the CEO in one line.

**Update:** (1) one sighting is a Field note; the rule body changes only on ≥2 runs, a CEO ruling, or an
artefact proving the old rule cannot work (ADR 0026) · (2) edit the owner skill only; point, never copy ·
(3) Knowledge: bump `verified:` · (4) a superseded rule keeps its old line with the evidence · (5) a skill
growing a second kind is split · (6) commit `skill(<name>): note|rule|flip — … — evidence …`.

## A skill that mixes Rules and Knowledge (CEO question 2026-09-27; CTO recommendation, pending his OK)

still be true?"**
- **No** — the rule exists because of how that platform behaves (never click Rerun on Higgsfield: it fires at
  once and bills). Keep it inside the Knowledge skill as a `HARD` line with `Why hard:` (ADR 0022 §7). Split
  off, it loses the fact that explains it, and an agent who opens the platform skill must meet it there.
- **Yes** — it is an org rule (ask the CEO with the exact amount before any paid generation). It moves to ONE
  Rules skill and the Knowledge skills keep a one-line pointer.

**The kind of a mixed skill is its main content — why an agent opens it.** Seedance with 14 platform-bound HARD
rules is Knowledge, correctly. Split a skill in two only when (a) a rule is org-wide and repeated elsewhere,
(b) the file is so large that its rules are buried, or (c) one part changes weekly and the other almost never.
