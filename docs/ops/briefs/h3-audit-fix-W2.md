### #2 [high] Reused warm VM: the runner's minute deadline counts from the VM's first take, not from this take
- Location: `scripts/colab/run_take.py:1244 (with try_reuse at 1157 and claim at 1117-1125)`
- Failure scenario: Default caps (45 min per take, 10 min idle stop). Take 1 starts at time T on a fresh VM, so vm_state.json gets started=T. It finishes at T+25 and the VM stays warm. Take 2 reuses the VM at T+26. try_reuse() loads the old state, so self.state['started'] is still T, and render_and_pull() sets deadline = T+45. At T+45, partway through take 2's render, the runner raises CapExceeded('minutes'): the in-flight scene's CU is wasted, the warm VM is torn down, and the remaining scenes go to RunPod as cap_minutes. Any take that reuses the VM after T+45 is killed right after CLEAN, upload and launch. The guard, which uses take.started, would have allowed take 2 until T+71. This affects every Auto Cut batch whose takes run back to back on one warm VM for more than 45 minutes in total.
- Evidence: run_take.py:1244 `deadline = self.state["started"] + self.take["max_minutes"] * 60`. try_reuse() at 1157 does `self.state = old`. claim() at 1117-1125 sets take.started but never touches state['started'] (the only other writer is Take.__init__ at 405). Every reused take inherits the first take's start: a grep for "started" in scripts/colab shows no other writer. The guard uses the take's own start (guard.py:192, 283), so the two clocks disagree. No test reuses a VM past 45 minutes: test_run_take.py has no render_and_pull or CapExceeded test, and the live run reused within minutes.
- Verified fix: In render_and_pull, base the deadline on the take's own start: `start = (self.state.get('take') or {}).get('started') or self.state['started']; deadline = start + self.take['max_minutes'] * 60`. This matches the guard's clock (claim() sets take.started on both the fresh and the reused path). Add a test that seeds vm_state.json with started = now - 50 min, runs a reused take, and checks it is not capped right away.
- Verified fix: In render_and_pull, take the start time from the take itself: `start = (self.state.get('take') or {}).get('started') or self.state['started']`, then `deadline = start + self.take['max_minutes'] * 60`. claim() sets take.started on both the fresh path and the reuse path, so this matches the guard's clock. Add a test to test_run_take.py that seeds vm_state.json with started = now - 50 min, reuses the VM, and checks that the new take is not capped straight away.

### #8 [medium] Warm reuse: the guard measures the take's CU against the previous take's start balance, which can kill a healthy take as cap_cu
- Location: `scripts/colab/guard.py:289-292 (stale baseline left by run_take.py:1157-1160 claim(), refreshed only at run_take.py:594 / 1051 via usage("cu_before") at 1305)`
- Failure scenario: Take 1 spends about 4.5 CU, then the VM idles for 8 minutes (about 1.2 CU on a G4). Take 2 reuses the VM. claim() saves take.cu_start=None, while the state-level cu_start still holds take 1's start balance. Before take 2's usage('cu_before') writes a fresh value, the guard polls. This window is a few seconds every time, and the guard is certain to hit it when try_reuse() restarts a dead guard, because a new guard polls at once. The poll also covers the whole take if that one `colab usage` call fails. The guard computes spent['take'] = old cu_start - balance, about 5.7 CU plus the gap, reaches the 6 CU cap and kills the VM. Take 2 ends as cap_cu after spending almost nothing, and its scenes and the warm VM are lost.
- Evidence: guard.py:289-292 first sets spent['take'] from st['cu_start'] and only overrides it when take.cu_start is not None. run_take.py:1157-1160 (try_reuse: `self.state = old`, then claim() with take.cu_start None and a save). The fresh value lands only at 1305 (`t.usage("cu_before")` -> StudioTake.usage at 1046-1054). Take.usage at 593-595 is what last wrote the state-level cu_start, during the previous take. Guard restart inside the window: 1164-1165.
- Verified fix: In guard.py:289-292, when a warm take is set, measure the take's balance drop only from take.cu_start, e.g. `base = take.get("cu_start") if take else st.get("cu_start")`, and set spent["take"] only when base is not None. Until then the take cap relies on est, which is computed from take.started. Optionally also set cu_start=None in StudioTake.claim() (run_take.py:1119) so the shared state never carries the previous take's baseline.

### #9 [medium] The VM watchdog starts only after every upload, and never starts in CLI-spec mode
- Location: `scripts/colab/run_take.py:1007 (call site in StudioTake.upload, 991-1008); CLI path Take.upload 483-497 / run() 603-645`
- Failure scenario: A fresh studio VM reaches READY, and the runner then runs the GPU probe (up to 3x40 s), CLEAN_CODE and the uploads: remote_take.py, the job, every ref and camera video, and every LoRA, each with a 600 s timeout. Only then does start_watchdog() run. If the Mac sleeps or loses its network in that window, the guard and the runner freeze with it, and nothing on the VM ends the rental until Colab's own runtime limit. That is open-ended billing, exactly the case vm_watchdog.py exists for. Takes started from a CLI spec (run(), Take.upload) never start a watchdog, so the whole take depends on the Mac staying awake.
- Evidence: StudioTake.upload (991-1008) calls self.start_watchdog() as its last step, after CLEAN_CODE (994) and all upload calls (999-1006). Base Take.upload (483-497) and run() (603-645) never call start_watchdog. watchdog_launch_code is idempotent and needs only vm_watchdog.py on the VM (1015-1018).
- Verified fix: In StudioTake.upload, move self.start_watchdog() from line 1007 to just after `s = self.session` (before the CLEAN_CODE exec at 994), so the dead-man switch is running before any long upload. Optionally also move start_watchdog up from StudioTake into Take and call it at the top of Take.upload, which covers CLI-spec takes too, since the guard already sends heartbeats to any named VM.

### #10 [medium] If `colab usage` fails on every poll, the per-take and VM CU caps are silently off
- Location: `scripts/colab/guard.py:299-300 (usage except branch inside the poll loop; compare the sessions-failure escalation at guard.py:271-281)`
- Failure scenario: A CLI update changes the 'Current balance:' line, or the usage endpoint keeps erroring. Then Colab.usage() raises ColabError on every poll, and the guard only logs 'usage failed', leaving spent and est empty, so decide()/decide_warm() never trips a CU cap. A take then runs to the 45-minute cap. On a G4 at about 8.9 CU/h that is about 6.7 CU against the 6 CU cap; on the H100 fallback it is well above. The 36 CU VM ceiling is likewise enforced only by time. A failing `colab sessions` already triggers a blind kill after 5 tries, but a failing `colab usage` never does.
- Evidence: guard.py:286-300: usage is wrapped in try/except ColabError that only logs. guard.py:270-281 shows the escalation that exists for sessions failures and has no counterpart for usage. colabctl.py:107-112 raises when BALANCE_RE does not match.
- Verified fix: In main(), add a usage_errors counter next to errors. Reset it to 0 after a successful colab.usage(). In the except at :299, increment it, and once it reaches 5 (with mine non-empty, no killed_reason, and the take/VM not closed), set killed_reason to "colab usage failing repeatedly", call write_kill_marker(state_path, killed_reason, (take or {}).get("id")) and kill(colab, st_k, mine, logf). That mirrors the existing sessions branch: kind "blind", the runner fails, and the queue routes the scenes to RunPod. About 10 lines in guard.py, plus a fake-CLI case in test_run_take.py where usage prints no balance.

### #11 [medium] retire_old ignores a failed release, kills the old guard, and the claim then erases the old VM from the shared state
- Location: `scripts/colab/run_take.py:1175 (retire_old), with the overwrite at run_take.py:1311-1319 (baseline, claim, save_state)`
- Failure scenario: The warm VM lists as `[?]` (its CLI record was pruned), so try_reuse() refuses it and retire_old() tries unassign_endpoint, which fails (timeout, or API error). stop_vms returns remaining=1, the result is discarded, and the old guard (the one process that remembered that endpoint) is sent SIGTERM. run_studio then takes baseline_endpoints (which now contains the orphan) and claim()/save_state() write a fresh vm_state.json with empty names and endpoints. The new guard does not know the orphan: it is not in the state, not in the CLI file, and it is excluded from orphan reaping because it is in the baseline. Teardown's absorb_vm_state cannot see it either. The orphan bills alongside the new VM until its own watchdog fires (15 min with no heartbeat, about 2.2 CU), or without limit if the old VM never got a watchdog.
- Evidence: run_take.py:1175 `stop_vms(...)` with the return value unused; 1176-1183 SIGTERM to the old guard regardless; 1311 baseline is taken after retire_old; 1317-1319 claim()/save_state() overwrite the shared file with the fresh self.state. guard.py:116 skips endpoints in the baseline, and remember() at 95-101 only knows what is in the state and the CLI file. A test (test_run_take.py:927-936) covers the failed unassign in teardown, not in retire_old.
- Verified fix: In retire_old, keep res = stop_vms(...). If res["remaining"] is not 0 (None counts as failure too), skip the SIGTERM to the old guard and raise ColabError("the previous VM could not be released") before run_studio takes the baseline and calls claim(). The finally block's teardown then runs absorb_vm_state on the untouched old vm_state.json and retries the release, the old guard keeps watching a state marked closed, and the scenes fall back to RunPod. Add a test case in the same suite using the existing fake world with an [?] VM and the unassign_fails file (test_run_take.py:900-936).

### #12 [medium] Live driver: SIGTERM skips the cleanup and leaves next dev plus a warm VM with a 60-minute idle stop
- Location: `scripts/live_colab_batch.py:401 (main, right after parse_args, before the deadman_only dispatch at 402-403; cleanup it protects is the finally at 628-648 and 349-362)`
- Failure scenario: The live batch runs for more than 75 minutes, so it is launched in the background. If it is stopped by SIGTERM or SIGHUP (task stop, session end, timeout wrapper), Python's default action ends the process without running the finally block. release_ours(), killpg(next) and safe_rmtree never run. next dev was started with start_new_session=True, so it keeps running, and the studio's guard keeps sending heartbeats to the warm VM, so its watchdog never fires. The script set colabIdleStopMin=60, so the VM bills for about 60 more minutes after the batch (about 9 CU on a G4), above the script's own 6 CU spend-abort limit, and the throwaway data dir and :4195 server stay behind.
- Evidence: live_colab_batch.py:457-458 Popen(..., start_new_session=True); 476 sets colabIdleStopMin 60; 628-648 cleanup only in finally; the script never installs a SIGTERM or SIGHUP handler, unlike run_take.py:1289-1292.
- Verified fix: In main() right after `a = ap.parse_args()` (line 401), install one handler for both signals: `signal.signal(signal.SIGTERM, h)` and `signal.signal(signal.SIGHUP, h)`. h first sets both signals to SIG_IGN, so a second signal cannot cut the cleanup short, then raises KeyboardInterrupt, so the finally blocks in main and in deadman_only (which main calls) always release the VM, kill next dev and remove the data dir. Optional, to also cover SIGKILL: lower colabIdleStopMin at line 476 from 60 to the shortest value that still leaves room for the measure step before the dead-man proof.

### #23 [low] try_reuse backing out after claim leaves the new VM with the old VM's clocks
- Location: `scripts/colab/run_take.py:1161 (back-out in try_reuse); fix goes in the warm fresh-VM branch of run_studio, run_take.py:1316-1318, before t.claim()`

### #24 [low] Pid-only checks for the lock holder and the old guard can be fooled by a recycled pid
- Location: `scripts/colab/run_take.py:1077 (acquire_lock) and scripts/colab/run_take.py:1164 (try_reuse); helper next to _pid_alive at run_take.py:952`

Use `_pid_runs(holder, "run_take.py")` at line 1077 (call ps once per new holder value, not on every 0.5 s loop), and `if not _pid_runs(guard_pid, "guard.py", str(self.state_path))` at line 1164.
