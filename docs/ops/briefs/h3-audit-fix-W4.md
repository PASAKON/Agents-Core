### #6 [high] finally block SIGTERMs whatever pid studio/.next/dev/lock names, which can be the LIVE :4100 studio
- Location: `/Users/gob/MoonieXHQ/Projects/MoonieX/ComfyRunpod/scripts/test_safe_split.py:955-963 (finally block; Popen at :303 has no start_new_session)`
- Failure scenario: Someone runs `python scripts/test_safe_split.py` from the main checkout, where the live studio (`next dev -p 4100`) holds studio/.next/dev/lock. Next 16 sees the lock and exits with 'Another next dev server is already running' (lockfile.js, process.exit(1)), so the test's own server never starts. wait() times out, and the finally block reads the lock, gets the LIVE server's pid and runs os.kill(pid, SIGTERM). The CEO's studio dies mid-render, and in-flight generate/render requests are lost (same class as the 09-26 :4100 restart incident). The queue runner also stops ticking, so a running pod has nobody to stop it until someone restarts the studio. A stale lock left by a crashed earlier run can also name a pid the OS has since given to an unrelated process.
- Evidence: test_safe_split.py:955-962 `lock_path = STUDIO_DIR / ".next" / "dev" / "lock"` ... `real_pid = json.loads(lock_path.read_text("utf8")).get("pid")` ... `os.kill(real_pid, signal.SIGTERM)` runs with no check that the pid belongs to this test. Popen at :303 has no start_new_session, so killpg is not available as the safe path. This suite is new in 0ec1c28..2cfea56; it copies the pattern from test_auto_cut.py:491-495 and test_scene_auto.py:910-918, which SIGKILL the lock pid mid-test and carry the same risk. The port guard (4190-4199) does not help: the lock is per studio folder, not per port.
- Verified fix: In test_safe_split.py, add start_new_session=True to the Popen at :303. In the finally block, replace the lock-pid read and os.kill with os.killpg(next_proc.pid, SIGTERM), then wait(10) and fall back to killpg SIGKILL, as test_balance.py:392 does. Before the Popen, refuse to start if studio/.next/dev/lock names a live pid (os.kill(pid, 0) succeeds), with the message 'a next dev already owns this studio folder (live studio?) - run in a worktree'. Optionally add the same check to test_auto_cut.py and test_scene_auto.py.
- Verified fix: Before the Popen at :303, read studio/.next/dev/lock if it exists. If the pid in it is alive (os.kill(pid, 0) succeeds), refuse with exit 2 and the message 'a next dev already owns this studio folder (live studio?) - run in a worktree'. In the finally block, SIGTERM the lock pid only when the lock's `port` equals this run's port (always 4190-4199, never 4100). Optionally also start next dev with start_new_session=True and stop it with os.killpg(next_proc.pid, SIGTERM). Apply the same guard to test_auto_cut.py:491 and test_scene_auto.py:910.

### #19 [medium] Settings PATCH is an unlocked read-modify-write over one fixed tmp file, so two near-simultaneous saves can drop a change (Allow Colab OFF or a lower CU cap) or corrupt settings.json
- Location: `studio/src/app/api/settings/route.ts:72-142 (readSettings ... writeSettings with no lock); studio/src/lib/settings.ts:76-81 (writeSettings, fixed `${FILE}.tmp`)`
- Failure scenario: On /settings the operator has an unsaved edit in 'Compute units per take' (say 20 -> 2) and then clicks the 'Allow Colab' checkbox to turn it OFF. Mousedown blurs the CU input, which sends PATCH {colabMaxCu:2} (page.tsx:496). The click then sends PATCH {safeSplit:{allowColab:false}} (page.tsx:403). If both handlers run readSettings() (route.ts:72) before either runs writeSettings() (route.ts:142), the second write replaces the first with a snapshot that lacks the other change. Both requests return 200 and the page shows the checkbox off and CU=2, but settings.json keeps either allowColab:true (getSafeSplit keeps routing safe takes to Colab after the operator turned it off) or maxCu 20 (the guard enforces 20 while the page shows 2). Both writers also share `${FILE}.tmp` (settings.ts:78). If a shorter payload is written over a longer one, the leftover bytes make invalid JSON, and that file is renamed into place. After that readSettings throws on every call: GET and PATCH /api/settings return 500, so the page cannot repair the file, and getSceneGenModel / getPromptFillDefaults throw, which breaks scene generation and prompt fill until someone edits the file by hand. getSafeSplit and getColabLimits fail closed, so this does not cause a safety leak.
- Evidence: route.ts:72-73 reads, validation runs, route.ts:142 writes, with no lock between the read and the write. settings.ts:76-81 writeSettings always uses the same tmp name `${FILE}.tmp`. settings.ts:66-73 readSettings rethrows any non-ENOENT error, including a JSON SyntaxError. Today's merges added five more keys and two page controls that save on blur or change (ColabLimitsSetting onBlur at page.tsx:496, SafeSplitSetting and AutoResumeSetting onChange), so one mouse action can now start two PATCHes. Only the settings page writes settings.json (grep for writeSettings).
- Verified fix: In settings.ts add a `withSettingsLock(fn)` promise-chain lock kept on globalThis (`__settingsLock`), copied from store.ts withEntitiesLock (store.ts:246-258). In route.ts PATCH, wrap everything from readSettings() (line 72) through writeSettings() (line 142) in it, returning the early 400 responses from inside the callback. Optionally give the tmp file a unique name with pid and randomUUID, so a writer outside the lock can never share it.

### #21 [medium] Colab limits card shares one error line: a rejected value stays in its input after another field saves and clears the error, so the page shows a cap the server does not enforce
- Location: `studio/src/app/settings/page.tsx:464`
- Failure scenario: The saved cap is 20 CU. The operator types 0.2 into 'Compute units per take' and tabs out. Client validation fails (below 0.5), so the shared err is set and the draft '0.2' stays in the input (page.tsx:459-461). The operator then changes 'Minutes per take' and tabs out. That save passes validation, calls setErr(null) (page.tsx:464), succeeds, and removes only the minutes draft. The card now shows CU = 0.2 with no error, while getColabLimits() and the guard enforce 20 CU per take. The operator leaves believing the spend cap is 0.2 CU. The same happens after a server 400 on one field followed by a successful save of another.
- Evidence: page.tsx:451-453 has one `err` state for all three fields. page.tsx:459-461 returns early on a validation failure and keeps draft[f.key]. page.tsx:464 clears err on any field's save. page.tsx:467-470 deletes only that field's draft. page.tsx:493 shows draft[f.key] ahead of the server value.
- Verified fix: In ColabLimitsSetting, store errors per field (useState<Record<string,string>>), clear only errs[f.key] when that field saves, and render each field's error under its own input. Alternatively, after a successful onSave, clear every draft (setDraft({})) so every input goes back to the server's body.colab values, or re-validate every field that still has a draft. About 10 lines, page.tsx only.
