### #0 [critical] Colab-running scenes count as pod work, so the RunPod pod is never drained or paused-stopped while a Colab take runs (and can stay up indefinitely after a keep-on hold lapses)
- Location: `studio/src/lib/queueRunner.ts:953 (also :944 and :360/:363 in recheckPendingStop)`
- Failure scenario: Case 1, bounded: an Auto Cut batch where take 1 is routed to RunPod and take 2 to Colab. RunPod finishes take 1 while the Colab take keeps rendering. Phase A finds no pending non-colab item (idx === -1), but `running` still counts the Colab scene, so the plan is `idle` instead of `drain`. The pod bills idle for the rest of the Colab take: up to 45 min by default, up to 240 min if the operator raises the cap. Case 2, low balance: the queue is paused with a Colab take running. fireOrHold passes `running.length` (Colab scenes included) to holdPaused, which returns at `running > 0`, so the pod is not stopped while the balance runs down. Case 3, unbounded: the pod is on a keep-on hold and the drain stop is refused (keepOn), which sets didWork=false and pendingStop=true. The hold lapses while a Colab take is pending or running. recheckPendingStop sees `stillWork` (Colab items count), sets pendingStop=false and returns. From then on every drain tick exits at `!rt.didWork && !rt.pendingStop` with the note 'nothing pending', and the pod is never stopped until RunPod work is queued again.
- Evidence: queueRunner.ts:936 `const running = q.filter((i) => i.status === "running")` (all backends). :940 `podRunning` excludes colab but is only used for AHEAD and pricing. :953 `if (running.length) { ... idle }` in the idx === -1 branch. :944 `{ kind: "hold", running: running.length }`. :282 holdPaused returns at `running > 0`. :360 `stillWork = q.some(pending || running)` and :363 `holdingForBalance ... !q.some(running)` count colab items. :364 sets pendingStop=false. :1030 drain returns at `!rt.didWork && !rt.pendingStop`. colabBackend.ts:520 states the intent: 'a Colab scene must never hold the RunPod pod awake'. startColabTake sets the head to `running` at claim (:847), before the VM is even up. No test in test_colab_backend.py covers the pod during a Colab take.
- Verified fix: Count only pod work in every 'may the pod stop' check: at :953 use `podRunning.length`; at :944 pass `running: podRunning.length`; in recheckPendingStop compute `stillWork` and the running check over items with `backend !== "colab"`. Then add a test to test_colab_backend.py for a mixed batch where the RunPod take finishes first and assert the pod is stopped while the Colab take is still running.
- Verified fix: In queueRunner.ts, every 'may the pod stop' decision should count pod work only:
- **:953** — use `podRunning.length`.
- **:944** — pass `running: podRunning.length`.
- **recheckPendingStop** — compute `stillWork` and the running check in `holdingForBalance` over `q.filter(i => i.backend !== "colab")`.

That is about 4 lines in one file. Add a test_colab_backend.py case: a mixed batch where the pod stops while the Colab take is still running.

### #3 [high] 'clear finished', or removing or retrying an already-done scene, cancels the whole running Colab take
- Location: `studio/src/lib/colabBackend.ts:476-477 (reconcileTake missing-member branch)`
- Failure scenario: A 4-scene take runs on Colab. S1 is done (it keeps backend colab and colabTakeId) and S2 is rendering. On /render the 'clear finished' button appears as soon as S1 is done, and the operator clicks it, which is DELETE /api/queue?finished=1. Clicking 'remove' on S1 does the same, and so does a PATCH retry of S1, which deletes S1's colabTakeId. On the next tick reconcileTake cannot find member S1 among the take's items while the outcome is `running`, so it sets cancel=true. reconcileColabTakes SIGTERMs the runner, which tears the VM down, and S2 to S4 go back to RunPod as colab_failed. The CU spent on S2 is lost and the pod boots to re-render three scenes. Separately, the DELETE also unchains S2 (its chainFromId target is gone), so S2 then renders on RunPod as a fresh head with no continuation.
- Evidence: colabBackend.ts:474-479: `const item = items.find(...); if (!item) { if (outcome.state === "running") cancel = true; continue; }`. The `scene` state is only read after this check (:480). queueRunner.ts:811 `for (const id of cancel) await cancelColabTake(id)`. render/page.tsx:1762-1767 shows 'clear finished' whenever any non-pending/non-running item exists. api/queue/route.ts:90 (clear finished) and :97 (remove) allow deleting done items. :52 the retry deletes colabTakeId.
- Verified fix: In reconcileTake, read the member's progress scene before the missing-item check. Cancel only when the take is still running and the missing member's scene is not done: move `const scene = view.progress?.scenes[m.index - 1]` above the `if (!item)` and change the condition to `outcome.state === "running" && scene?.state !== "done"`. Removing a pending member (the case the comment intends) still cancels the take, while clearing or removing a finished one, or retrying it, leaves the running take alone.
- Verified fix: In reconcileTake, read the progress scene before checking for the item. Cancel only when the missing member's scene isn't done yet: move `const scene = view.progress?.scenes[m.index - 1];` above the `if (!item)` check and make that branch `if (outcome.state === "running" && scene?.state !== "done") cancel = true;`. Removing a scene that hasn't rendered yet still cancels the take. A retried done S1 then goes to RunPod as colab_unavailable through takeMembers returning null, which does no harm. Add a test to test_colab_backend.py: remove a done member mid-take and assert the runner is not cancelled.

### #4 [high] Keep-on recheck drops pendingStop when the remaining work never runs on the pod, so the pod is never stopped
- Location: `studio/src/lib/queueRunner.ts:364 (recheckPendingStop)`
- Failure scenario: 1) The queue drains while a keep-on hold is set. attemptStopHeldPod takes the keepOn branch and sets didWork=false, pendingStop=true, plus a timer for the hold's end. 2) During the hold the operator enqueues work that all routes to Colab. 3) At hold expiry (or Release via DELETE /api/pod/keep-on), recheckPendingStop sees stillWork=true (Colab pending/running counts) and holdingForBalance=false, so it sets pendingStop=false and clears the timer, expecting 'the normal tick path takes back over'. 4) The tick never fires anything on the pod, so didWork stays false. When the Colab work ends, the drain branch hits `!rt.didWork && !rt.pendingStop` and notes 'nothing pending'. The pod bills idle with no end. The same strand happens if the remaining RunPod item fails in phase B/C (could not continue / could not start) without ever setting didWork.
- Evidence: queueRunner.ts:360 `const stillWork = q.some((i) => i.status === "pending" || i.status === "running")` (Colab included); line 364 `rt.pendingStop = false; clearPendingStopTimer(); return;`; attemptStopHeldPod:330 sets `rt.didWork = false` on a keep-on refusal; drain gate at 1030 `if (!rt.didWork && !rt.pendingStop) { rt.note = "nothing pending"; return; }`; didWork is set only at 1180, on a pod fire.
- Verified fix: In recheckPendingStop, when stillWork && !holdingForBalance, only clear the timer and leave pendingStop true (line 364 becomes `{ clearPendingStopTimer(); return; }`). The drain gate at 1030 then still stops the pod once nothing renders: the fire path sets didWork anyway, and holdPaused already treats pendingStop as a stop that is still owed. Optionally, also count only non-Colab items (backend !== "colab") in stillWork at line 360.
- Verified fix: At queueRunner.ts:364, when stillWork && !holdingForBalance, clear only the timer (clearPendingStopTimer(); return;) and leave rt.pendingStop true. The drain branch at line 1030 then still owes the stop. It retries once nothing renders, behind its existing busy-jobs guard, and holdPaused at line 283 already treats pendingStop as a stop still owed. Don't take the 'count only non-Colab items' half of the hint. It would stop the pod in the middle of a Colab take, and then a colab_failed fallback has no pod to land on.

### #5 [high] A pod started for a queue whose work all routes to Colab is never stopped (didWork never set)
- Location: `studio/src/lib/queueRunner.ts:1030 (drain gate on rt.didWork; rt.didWork is set only at :1180 on a pod fire) and studio/src/lib/podRuntime.ts:391 (fireRetry hasWork counts Colab items)`
- Failure scenario: safeSplit.allowColab is on. The operator enqueues an episode that routes entirely to Colab and presses Start Pod, as they always did before Colab existed. Alternatively, the NO_CAPACITY retry loop boots one: fireRetry treats Colab-only work as 'hasWork'. Every take finishes on Colab, the runner never fires on the pod, didWork stays false, and the drain branch reports 'nothing pending'. The pod bills idle until someone presses Stop. Before Colab, a pod started for a non-empty queue was always used and then stopped.
- Evidence: queueRunner.ts:1030 drain gate on didWork, which is set only at 1180 (pod fire); podRuntime.ts:391 `const hasWork = q.some((i) => i.status === "pending" || i.status === "running")` counts backend==='colab' items as a reason to boot a RunPod pod.
- Verified fix: Two parts. Small: in fireRetry, count only items that will use the pod (`i.backend !== "colab"` and pending or running), so the retry loop never boots a pod for Colab-only work. Needs a decision: in the drain branch, also stop a ready pod the runner never used when the queue had work at the moment the pod came up (for example, a flag set when phase B first sees the pod ready while items are pending or running). The other option is to warn or refuse Start Pod on /render when every pending item is routed to Colab. Separately, decide whether :953 should check podRunning instead of running.
- Verified fix: In fireRetry (podRuntime.ts:391), count only RunPod work: `q.some((i) => i.backend !== "colab" && (i.status === "pending" || i.status === "running"))`. Then the retry loop never boots a pod for Colab-only work (one line, no design decision). Separately, the CEO should decide whether /render warns, or the runner stops a ready pod it never used, when the operator presses Start Pod and every pending item is on Colab. That reverses the manual-pod rule, so it should not be auto-applied.

### #28 [low] Auto-resume prices the first pending item even when it is a Colab scene, not the RunPod clip the gate refused

- Verified fix: Change line 249 to `const next = q.find((i) => i.status === "pending" && i.backend !== "colab");` so auto-resume picks the same clip that phase A picks and the gate prices.
