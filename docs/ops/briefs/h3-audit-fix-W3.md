## Findings

### #1 [critical] Reopening /scenes while an old job is still running replaces the newer saved plan or story, then autosave writes over that draft
- Location: `studio/src/app/scenes/page.tsx:653 (init's auto-adopt), with adoptJob at 503-531 and writeDraft at 718-740`
- Failure scenario: Job A is still writing (a 9-scene batch takes minutes). The operator presses Re-plan anyway and gets plan P2, so the draft saves jobId null. Pressing Discard draft and typing a new story leaves the draft in the same state. The operator then opens /entities or /render and comes back, or reloads. Init finds that the newest job is running and the restored draft has no jobId, so it calls adoptJob(A). That puts A's plan, story, characters, setting, model, aspect, style and seconds into the form, sets the cards to [] and switches a fixed-mode page to auto. draftIdRef already holds the restored draft's id (line 624). About 2.5 s later the throttled autosave POSTs this state with that id, and the draft route updates that draft in place. P2 (which cost money to plan) or the newly typed story is gone for good. This also contradicts the Re-plan confirm text (line 1875), which says the job stays reachable from 'Show last written batch', meaning it is offered, not forced. Test S5 only checks a finished job, so the running case is not tested.
- Evidence: page.tsx:650-655 `if (newest) { if (newest.status === "running" && !restored?.jobId) adoptJob(newest); else setLastJob(newest); }`. adoptJob (503-531) calls setPlan, setStory, setCharacters, setMode("auto") and setCards([]). Line 624 `draftIdRef.current = latest!.id`. writeDraft (730) sends `id: draftIdRef.current`. draft/route.ts:27-34 replaces that draft in place. doPlan (1020) and discardDraft (776) both persist jobId null.
- Verified fix: At page.tsx:653, auto-adopt only when nothing in the draft can be lost: either there is no restored draft, or the draft has no jobId, no cards, and a plan equal to the running job's plan (JSON.stringify(restored.plan) === JSON.stringify(newest.plan); this is the original jobId-null case). Otherwise call setLastJob(newest), so the running job shows up as the '(N scenes, running)' offer and the lastJobRunningElsewhere poll keeps it fresh. Add a scenes UI case: start a job, Re-plan anyway, reload, then check that the new plan is still there and the job is offered rather than adopted.
- Verified fix: At page.tsx:653, auto-adopt the running job only when the draft cannot be lost: there is no restored draft, or the draft has no cards and its plan and story are each empty or the same as the job's (the CEO's original jobId-null case). In every other case call setLastJob(newest), so the job is offered as 'Show last written batch (N scenes, running)' instead of replacing the draft. Add a test_scenes_ui.py case: start a job, press 'Re-plan anyway', reload while the job runs, and check that the new plan is still shown and the running offer is there.

### #14 [medium] Re-plan, 'Show running job' and 'Show last written batch' drop edited cards, the plan and the form with no confirm
- Location: `studio/src/app/scenes/page.tsx:1076 (requestReplan), with the confirm box at 1872 and the two attach buttons at 1759 and 1918`
- Failure scenario: (a) This merge moved Re-plan out of the `!job &&` block, so it now shows beside a finished or stopped job. requestReplan only asks when job.status is running. On a done job whose cards the operator has hand-edited or regenerated (paid), one click runs doPlan, which sets the cards to [] (line 1022), and autosave writes over the single draft. 'Show last written batch' brings back only the job's unedited text, so the edits are lost. (b) The operator presses Re-plan anyway (new plan P2) and then Write all, which returns 409 because A is running. The page offers 'Show running job' (line 1918) with no hint. Clicking it calls adoptJob(A), which replaces P2 and the form and is persisted 2.5 s later. 'Show last written batch' (line 1759) does the same; its hint mentions only the plan, not the form or edited cards.
- Evidence: Re-plan button at 1861-1869 now renders whatever the job state. requestReplan 1076-1079: `if (job?.status === "running") setReplanAsk(true); else void doPlan();`. doPlan 1020-1022 sets jobId, job and cards to null/[]. attachJob 542-555 leads to adoptJob, which calls setCards([]) and replaces the form. Autosave keeps one draft id and updates it in place.
- Verified fix: In requestReplan, also ask when `cards.length > 0`, not only when `job?.status === "running"`. Show the confirm box on `replanAsk` alone (not `replanAsk && job`), and make its text depend on the case: the running-job sentence only when a job is running, plus a line saying the cards on screen will be cleared. Send both attach buttons through the same inline confirm with one pending-action state (replan, or attach plus the job id). Ask whenever the page holds cards or a plan that differs from the target job's plan. Say plainly that the plan, the form and the cards will be replaced.

### #15 [medium] Stop does nothing during the audit, but the page shows a Stop button next to 'Auditing · rewrite k/n'
- Location: `studio/src/app/scenes/page.tsx:1895 (Stop button); root cause studio/src/lib/sceneJob.ts:398-465 (runAudit loop has no stop check)`
- Failure scenario: All scenes are written and the audit flags 6 scenes. The page shows 'Auditing · rewrite 1/6' with a Stop button (page.tsx:1895-1898, shown whenever status is running). The operator presses Stop. stopJob adds the id to runtime.stopRequested, but runAudit never checks that set. Every paid rewrite and recheck still runs, the job ends 'done', and runJob's finally clears the flag. The click is silently ignored. The new stage and counter line now makes this phase visible and invites the click.
- Evidence: sceneJob.ts: the only check is in writeAllScenes (281 `if (runtime.stopRequested.has(job.id))`). runAudit (332-470) has no stop check. runJob 492-494 deletes the flag in finally. page.tsx:1895 `{job.status === "running" && (<button ... onClick={() => void doStop()}>`.
- Verified fix: In page.tsx:1895, show Stop only when job.status === "running" && job.auditStatus !== "running". During the audit, put a short muted note in its place saying the audit finishes on its own. Also make the stop route return 409 while auditStatus is "running", so a stale page can't get a false ok. Actually honoring Stop inside runAudit (break the loop and mark the remaining flagged scenes amber) is a separate design call, since Resume would rerun the whole audit.

### #16 [medium] Card edits and paid per-card regenerates made while a job runs are overwritten by the next poll (now also after a re-attach)
- Location: `studio/src/app/scenes/page.tsx:2033-2092 (the card controls). Root cause is the job-to-cards sync at 1153-1175, together with line 1109.`
- Failure scenario: A job is writing S5. The operator edits S1's text, or presses regenerate on S1 (a paid OpenRouter call). Within 2 s the poll calls setJob. The job-to-cards sync runs because autoSyncDone is false while the job runs, and it rebuilds every card from the job record. S1 goes back to the job's text, and the regenerate cost is wasted. The terminal poll does the same once more before autoSyncDone becomes true. Before this merge a draft restored mid-job kept its cards (autoSyncDone was true). The new line 1109 resets autoSyncDone on every running poll, so edits restored from a draft are now overwritten too. Title, prompt and regenerate stay enabled the whole time, while Send is already disabled in this state.
- Evidence: page.tsx:1109 `if (body.job?.status === "running") autoSyncDone.current = false;`. Sync effect 1153-1175 calls setCards(attempted.map(...)) from job.scenes. Card inputs 2033-2038 and 2059-2065, and regenerate 2046-2055 (disabled only when regenBusyIdx === idx), have no running guard. Send at 2155 is disabled when `mode === "auto" && job?.status === "running"`.
- Verified fix: Compute `const jobRunning = mode === "auto" && job?.status === "running"` once. Add it to the `disabled` of each card's title input, prompt textarea, seconds input, resolution select, include checkbox and regenerate button (OR it into the existing regenerate condition), with a title tooltip saying the scene can be edited when the batch finishes, which matches the Send guard at 2155.

### #18 [medium] Showing a job written with the cut Off, while the page has a cut set, blocks Send and locks the cut control
- Location: `studio/src/app/scenes/page.tsx:503-531 (adoptJob), with the effect at 1144-1147 and the gates at 1221-1227`
- Failure scenario: The page's chainLength is N, from the Settings default after a Discard or from the draft. The operator clicks 'Show last written batch' for a done job written with the cut Off (input.chainLength absent). adoptJob does not touch chainLength. The jobChainLength effect only applies a non-null value, so chainLength stays N. cutStale is then `jobChainLength(null) !== N` and hasBlockingError disables Send. chainLocked is true (jobId set, and chainAdoptable needs a stopped job), so the select is disabled. The hint tells the operator to 'press Resume ... or set it back', but a done job has no Resume and the control is locked. The adopted batch cannot be queued without discarding it.
- Evidence: adoptJob 503-531 never calls setChainLength. 1144-1147 `if (jobChainLength) setChainLength(jobChainLength);`. 1221-1227 chainAdoptable/chainLocked/cutStale. Select at 1606 `disabled={chainLocked}`. Hint at 2127.
- Verified fix: In adoptJob, add `setChainLength(cleanChainLength(inp.chainLength));` next to the other input setters. The page then takes the job's cut, including Off. A stopped job with no cut keeps chainAdoptable, so the operator can still pick N before Resume. One caveat: a draft already saved in this bad state (chainLength N with the jobId of a job that has no cut) will hit the same lock again when it is restored on reload.

Use a normal fetch (no keepalive, because of the ~64 KB body cap); writeDraft already skips empty drafts and setDraftId after unmount is harmless.
