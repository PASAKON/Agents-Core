## Findings

1. **P1 — Unknown publisher liveness is treated as absence.** `runners/coo_dispatch.py:303` reads only `live_sessions`; `:487` proceeds when that query succeeds with an empty list. It never checks `live_hosts.error` or `published_at`. A failed publisher retains its previous rows and timestamp (`tools/live_sessions.py:161`, `:696`), so an old empty snapshot is not proof that no role is alive. A session outside the expected lowercase `<role>-*` tmux naming convention can then escape the tmux check (`runners/coo_dispatch.py:525`). The flock does not cover its lifetime: the launcher releases it after writing its PID lock (`scripts/cxo-claude.sh:480`). The launcher's additional PID check is conditional on `ORG_SINGLE_CLEVEL` (`:452`), and its helper treats unreadable PID locks as absent (`tools/clevel_gate.py:145`). Thus the new dispatcher does not independently guarantee fail-closed singleton behavior. Require a fresh, successful Contabo liveness publication, fail closed on missing/error/stale metadata, and use an atomic role reservation plus reliable local process checks for the launch handoff. Test an unreadable publisher with a previously empty snapshot and an existing role outside the expected tmux name.

2. **P2 — Clock rollback drops prior requests from both limits.** `lib/coo_policy.py:116` ignores an event more than 60 seconds in the future; `:118` also excludes it from the daily total. Reproduced directly: a CTO event at `2026-10-26T04:02:00Z`, checked at `04:00:00Z`, returns `None` (allowed), whereas an event at `03:59:00Z` blocks. A backward correction over 60 seconds, or this much gate/dispatcher clock skew, therefore defeats both layers. There is also a dispatch-time gap: `runners/coo_dispatch.py:470` counts request creation times, not actual starts. A delayed old request can start now and be followed by a new request within ten minutes if the first session exits. Fail closed on future/invalid timestamps and enforce launch limits against durable dispatcher reservations/start times using a consistent clock. Add rollback and delayed-queue tests.

3. **P2 — Error redaction does not cover every DSN format.** `scripts/resolve-resume-id.sh:36` removes only `postgres://` and `postgresql://` tokens before forwarding the last stderr line at `:50`. A stub hub error containing `host=db user=org password=REVIEW_FAKE_VALUE dbname=hub` reproduced a plaintext password in resolver stderr (exit 2). Keyword DSNs and separately printed passwords are untouched. Prefer a fixed error category rather than arbitrary backend stderr, or comprehensively redact supported credential formats. The related new dispatcher error path at `runners/coo_dispatch.py:491` also copies arbitrary root-side exception text into the COO-readable completion event without redaction; keep private exception details out of those events. Add synthetic secret-bearing error tests for both paths.

4. **P2 — The SQL request guard accepts a JSON null role.** At `deploy/coo-gate/org_coo_role.sql:145`, `NULL NOT IN (...)` evaluates to NULL. With `task_id=NULL` and payload `{"role":null,"host":"contabo","by_session":"x"}`, all other rejection terms are false, the IF condition is NULL, and the trigger returns NEW at `:150`. This violates the promised fixed-role constraint. Use a null-safe allowlist predicate, such as `(role_value IN (...)) IS DISTINCT FROM TRUE`, and test the actual PostgreSQL trigger with JSON null and wrong JSON types. The Python dispatcher still rejects this payload, so this is a database boundary defect, not a demonstrated root launch bypass.

## Answers to the seven checks

1. **Launch-input boundary: passes for the new respawn operation.** Gate extra keys are rejected at `runners/coo_gate.py:217`; policy validates the exact lowercase role and `contabo` at `lib/coo_policy.py:58`. Root independently validates the exact payload keys and role/host at `runners/coo_dispatch.py:444`. The caller's `session_id` does reach the root-readable event as `by_session` (`runners/coo_gate.py:243`), but is never used for argv, env, prompt, tmux name, filesystem path, or resume UUID. Root chooses the previous session from its database (`runners/coo_dispatch.py:389`), accepts only a full hex UUID from the resolver (`:414`), or mints a fresh hex SID (`:544`). Launch construction is at `:419`. No caller-controlled prompt/environment/path reaches that construction. This conclusion is scoped to respawn, not a claim that existing worker operations accept no text.

2. **Singleton/fail-closed: incomplete; finding 1.** Verified and unverified hub rows block by role, recognized display name, or address/SID (`runners/coo_dispatch.py:315`). A SQL read exception or malformed non-list blocks (`:488`, `:494`); malformed individual rows block (`:317`). Flock open/acquire errors block (`:106`); tmux execution errors or a nonzero result return unknown and block (`:88`, `:519`). Database reads for request history/latest SID that raise abort the step before launch. However publisher health/freshness is never read, and checking then releasing a flock is not a lifetime lock. The existing launcher provides conditional additional protection, not an unconditional proof.

3. **Rate limits: mixed case and many caller sessions do not partition the quota; clock edges can bypass it.** Exact membership rejects `CTO`/`Cto` (`lib/coo_policy.py:60`), and counting filters by role only, never `by_session` (`:110`). The dispatcher rechecks prior requests independently (`runners/coo_dispatch.py:468`). Exactly ten minutes permits a new request; the daily boundary is Asia/Bangkok, and the rolling ten-minute window still spans midnight. Both limits are per role; there is no global three-starts/day cap across all roles. If the brief intends a global daily cap, that is an additional required change. See finding 2 for rollback and queue-age weaknesses. Direct database holders can also supply `events.ts` (`org_coo_role.sql:97`); the trigger does not validate it. The stated socket caller cannot supply that field.

4. **Event privileges: narrowly scoped; trigger has the NULL gap above.** `events` receives only five-column INSERT (`deploy/coo-gate/org_coo_role.sql:97`); direct SELECT is revoked at `:86`–`:87`. The view has `security_barrier` and filters request/done kinds (`:98`). Literally, org_coo DOES SELECT other relations: `tasks` (`:93`), five `c_level_sessions` columns (`:102`), three `live_hosts` columns (`:106`), and ten `live_sessions` columns (`:108`), all pre-existing operational grants. For event data, only the new view is readable. Section 6 still excludes `events` from its SELECT allowlist and checks effective mutation privileges (`:193`, `:219`). It does not prove exact SELECT columns within allowed relations, view options, or trigger behavior. The three triggers remain attached (`:176`). `coo_respawn_done` cannot be forged by org_coo through normal INSERT: it is excluded by the kind guard (`:152`), and UPDATE/TRIGGER privileges are not granted. Live PostgreSQL execution of this proof was not performed.

5. **Resume identity and injection: passes on the dispatcher path.** Explicit resume resolution is quoted (`scripts/cxo-claude.sh:114`); the resumed UUID's final eight hex characters become SID (`:366`), and a random new UUID with that suffix is generated (`:413`). The CLI receives the destination via `--session-id` (`:926`); the existing fork behavior preserves the source resume argument. Explicit `--session` retains precedence (`:364`), so the suffix assertion is not universal for callers deliberately overriding SID. Invalid tmux suffixes are rejected as identity inputs and replaced with a fresh ID (`:381`–`:393`); the launcher does not reject the whole launch. Quoted shell data and hex validation prevent shell injection through these tmux names/resume IDs. The root launch command is built only from fixed roles, a trusted repo path, and validated UUIDs.

6. **Resolver errors: not fully redacted; finding 3.** URL schemes are removed case-insensitively, but keyword DSNs remain. `mktemp` creates the stderr file at `scripts/resolve-resume-id.sh:30`; EXIT cleanup is installed immediately (`:31`) and the normal path also removes it (`:40`). The synthetic failure probe left no `resolve-resume-err.*` files. This covers ordinary exit paths, not uncatchable process termination.

7. **Public diff: no apparent live credentials found.** There ARE literal password-bearing DSNs in test fixtures (`tests/test_resolve_resume_id.py:67`, `:84`); context identifies these as synthetic redaction test strings, not evidence of a real deployed credential. Do not describe the diff as containing no DSN literals. No new private key, production password, or live token was identified by inspection and targeted added-line scanning. This is not a credential-validity check.

## Verdict

**changes-needed**

Required changes:
1. Fail closed on missing, stale, or failed liveness publication and make singleton launch handoff atomic with reliable local liveness checks.
2. Make rate accounting robust to future timestamps/clock rollback and delayed dispatch; clarify whether the daily cap is per role or global.
3. Stop returning arbitrary credential-bearing backend errors from the resolver and root dispatcher; add redaction regressions.
4. Reject JSON-null roles in the SQL trigger and validate the real PostgreSQL grants/guards, including forbidden completion-event insertion.
