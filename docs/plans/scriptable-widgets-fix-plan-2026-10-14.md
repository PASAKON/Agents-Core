## 2. บัค เรียงตามความถี่ที่ CEO น่าจะเจอ

> ความถี่ยังเป็น **การประมาณ** ยังไม่ใช่ตัวเลขวัดจริง: server ไม่เก็บ log การเรียก (`serve.py` ปิด log ไว้ และ traefik ก็ไม่มี access log) เลยนับไม่ได้ว่ามือถือดึงข้อมูลบ่อยแค่ไหนหรือพลาดกี่ครั้ง ข้อ 2.10 คือการติดตัววัดเพื่อให้ได้เลขจริง

### 2.1 ตัวเลขย้อนกลับไปเป็นของเก่า 3–5 สัปดาห์ (Claude · Codex · AGY): **อันดับ 1**
- **อาการ:** ปกติตัวเลขสด แต่บางครั้งกลายเป็นตัวเลขเก่าโดยไม่มีอะไรบอก แล้วรอบถัดไปก็กลับมาสดเอง
- **สาเหตุ + หลักฐาน:**
  - `loadData()` ใน `Claude Usage.js:61-66`, `Codex Usage.js:76-81`, `Agy Usage.js:81-86`: ถ้า URL ล้ม → อ่าน iCloud → `saveLocal(d)` เขียน **อะไรก็ได้ที่ได้มา** ทับ cache ในเครื่อง ไม่มีการเทียบว่าอันไหนใหม่กว่า
  - ไฟล์ iCloud ไม่มีใครเขียนแล้ว (stat บน Mac 14 ต.ค.): `claude-usage.json` 09-05 20:25 · `codex-usage.json` 09-22 21:33 · `agy-usage.json` 09-22 21:33
  - ตัวเขียน Codex/AGY ฝั่ง Mac ถูกลบไปแล้วใน commit b7b7d75 (23 ก.ย.) แต่ widget ยังอ่านไฟล์นั้นเป็นทางสำรองอยู่
  - ตัวเขียนฝั่ง Claude (`com.mooniex.claude-usage-sync`) ล้มทุก 10 นาที: `last exit code = 1` และ `/tmp/claude-usage-sync.err` มีบรรทัด "WRITE FAILED to iCloud — grant Full Disk Access to /bin/bash" ซ้ำไปถึง 2026-10-13T20:19Z โดย CEO เลือกไม่ให้ Full Disk Access (commit b7b7d75)
  - ป้ายเตือนโชว์แค่ "⚠ 20:25" ไม่มีวันที่ ข้อมูลอายุ 39 วันจึงดูเหมือนเป็นเวลาของวันนี้
- **วิธีแก้ (เปลี่ยนแค่ข้อมูล layout เหมือนเดิม):**
  1. ตัดเส้นทาง iCloud ออกจาก Codex/AGY/Claude (ไม่มีใครเขียนไฟล์นั้นแล้ว)
  2. **เอาอันที่ใหม่ที่สุดเสมอ**: เทียบเวลาของข้อมูล (`generated_at` / `observed_at`) ระหว่างของที่ดึงได้กับ cache แล้วไม่เขียน cache ทับด้วยของที่เก่ากว่า
  3. ป้าย ⚠ ใส่วันที่เมื่อข้อมูลไม่ใช่ของวันนี้ ("⚠ 5 ก.ย. 20:25") โดยใช้ช่องข้อความเดิมและฟอนต์เดิม
  4. ปิดงาน launchd `com.mooniex.claude-usage-sync` บน Mac (`launchctl bootout` + ลบ plist) เพราะรันทุก 10 นาทีแล้วล้มทุกครั้ง
- **ความเสี่ยง:** ต่ำ ถ้า VPS ล่มนาน widget จะโชว์ cache ล่าสุดพร้อม ⚠ และวันที่ ซึ่งยังดีกว่าโชว์ข้อมูลเดือนก่อน งาน launchd ของ CFO (`com.mooniex.cfo-claude-usage`) ไม่เกี่ยวกับงานนี้ ไม่แตะ

### 2.2 อายุข้อมูลและเวลานับถอยหลังค้าง ดูเหมือนสดทั้งที่เก่า (ทั้ง 5 ตัว): **อันดับ 2**
- **อาการ:** RAM/Disk เขียนว่า "อัปเดต 6 นาที" หรือ Claude เขียนว่า "รีเซ็ตใน 2 ชม." แต่ข้อความนั้นอาจค้างมาหลายชั่วโมงแล้ว
- **สาเหตุ + หลักฐาน:**
  - `ago()` / `countdown()` คำนวณครั้งเดียวตอน render: `Disk Monitor.js:77-84`, `RAM Monitor.js:80-87`, `Codex Usage.js:84-101`, `Claude Usage.js:69-77`
  - iOS refresh widget ตามโควตาของมันเอง (Apple ให้ราว 40–70 ครั้ง/วัน/widget ตัวเลขจากเอกสาร Apple ไม่ได้วัดจากมือถือ CEO) ส่วน `refreshAfterDate` เป็นแค่คำขอ: Claude กับ AGY ขอทุก 5 นาที (288 ครั้ง/วัน) ทั้งที่ข้อมูล AGY เปลี่ยนแค่ทุก 15 นาที
- **วิธีแก้:**
  1. ใช้ `WidgetDate` + `applyRelativeStyle()` ของ Scriptable ในช่องข้อความเดิม ให้ iOS เดินเวลาเองโดยไม่ต้อง refresh (ทั้งอายุข้อมูลและเวลานับถอยหลัง)
  2. ตั้ง `refreshAfterDate` ตามรอบของแหล่งข้อมูล: Claude 5 นาที, AGY/Codex 15 นาที, Disk ตามตารางของ hub (ทำอยู่แล้ว), RAM 10 นาที
- **ความเสี่ยง:** ปานกลาง ข้อความที่ iOS สร้างให้อาจสะกดต่างจากเดิมเล็กน้อย (ภาษาตาม locale ของเครื่อง) → ต้อง preview บนมือถือจริงก่อน ถ้า CEO ไม่ชอบ ใช้เวลาแบบ "03:12" (มีวันที่ถ้าไม่ใช่วันนี้) แทน **ข้อนี้ต้องให้ CEO เลือก**

### 2.3 Claude ค้างยาวเมื่อ login ของ Contabo หลุด: **อันดับ 3 (เกิดไม่บ่อย แต่แต่ละครั้งนาน)**
- **อาการ:** Claude widget ไม่ขยับเป็นชั่วโมงหรือเป็นวัน
- **สาเหตุ + หลักฐาน:**
  - `monitor.py:186-206` refresh token ด้วย `claude -p ok --model claude-haiku-4-5` ไฟล์ credentials เป็นไฟล์เดียวกับที่ทุก session ของ root ใช้ (`/root/.claude/.credentials.json`) login หลุดเมื่อไหร่ monitor ก็ล้มทุกรอบ
  - journal: 9 ต.ค. 14:53 → 10 ต.ค. 03:48 ล้ม **194 รอบติดกัน (ค้าง ~13 ชม.)** ตรงกับ LungNote 20ed74b1 ("Contabo root Claude login น่าจะหลุดตั้งแต่ 9 ต.ค. 14:49") ก่อนหน้านั้น 21 ส.ค. → 5 ก.ย. ค้าง 15 วัน (LungNote 8bba985c) และล้มเดี่ยวๆ 6 ต.ค. 07:36 และ 15:31 ตอน weekly = 100%
  - `capture_output=True` แต่ไม่เคยเอา stderr มาบันทึก → log มีแค่ "returned non-zero exit status 1" จึงไม่เคยรู้สาเหตุจริง
  - unit `TimeoutStartSec=90` สั้นกว่า timeout ของ subprocess (120 วิ) → systemd ฆ่าก่อนที่จะได้ error ของตัวเอง
  - ตอนล้ม monitor ไม่เขียนอะไรลงไฟล์เลย widget จึงรู้แค่ว่า "เก่า" แต่ไม่รู้ว่า "เพราะอะไร"
- **วิธีแก้:**
  1. ก่อน refresh ให้อ่านไฟล์ credentials ใหม่ เพราะ session อื่นอาจ refresh ไปแล้ว (mtime ล่าสุด 21:57 CEST คือมีคน refresh ให้อยู่เรื่อยๆ)
  2. บันทึก stderr 300 ตัวอักษรสุดท้ายลง journal โดยลบทุกอย่างที่หน้าตาเหมือน token ออกก่อน
  3. แก้ `TimeoutStartSec` เป็น 150
  4. เวลาล้ม ให้เขียน `status: "error"`, `error`, `last_ok_at`, `fail_count` ต่อท้าย usage.json โดยเก็บตัวเลขเดิมไว้ (field ที่เพิ่มไม่ทำให้ widget ตัวเก่าพัง)
  5. widget โชว์ "⚠ <วันที่ เวลา>" ในช่องเดิม ส่วนรายละเอียดอยู่ในหน้า detail
  6. ล้มติดกัน ≥ 8 รอบ (~30 นาที) → แจ้ง C-level ที่ดูแลผ่านช่องทาง notify ของ org **ไม่ใช่อีเมล CEO**
- **ความเสี่ยง:** ต่ำ ถ้า login หลุด monitor ก็แก้ไม่ได้อยู่ดี แต่ CEO จะเห็นว่าค้างและรู้สาเหตุ

### 2.4 widget ว่างเปล่า / ไม่แสดงผล: **อันดับ 4 (อนุมาน ยังไม่เคยจับได้คาหนังคาเขา)**
- **อาการ:** widget ว่าง หรือค้างภาพเก่าของ iOS ไว้
- **สาเหตุที่เป็นไปได้ + หลักฐานในโค้ด:**
  - เส้นทางสำรองใช้เวลาไม่มีเพดาน: `fromURL` 8 วิ แล้วตามด้วย `downloadFileFromiCloud(p)` ที่ไม่มี timeout (`Claude Usage.js:50`, `Codex Usage.js:65`, `Agy Usage.js:70`) ไฟล์ iCloud อายุ 3–5 สัปดาห์น่าจะถูก iOS ย้ายออกจากเครื่องไปแล้ว จึงต้องโหลดใหม่ และถ้าเน็ตแย่ iOS อาจฆ่า script ก่อนเสร็จ
  - ถ้า render เจอข้อมูลหน้าตาแปลก script จะ throw แล้ว Scriptable โชว์กล่อง error แทน widget เช่น `RAM Monitor.js:240` `r.h.mem.total` ไม่มีตัวกัน (ตอนนี้ hub ตรวจ `mem` ให้อยู่แล้ว ความเสี่ยงจึงต่ำ)
- **วิธีแก้:**
  1. ตัด iCloud (ตามข้อ 2.1)
  2. งบเวลารวม ≤ 12 วิ: ดึงครั้งแรก timeout 6 วิ → พลาดรอ 1.5 วิ แล้วลองใหม่ timeout 4 วิ → ยังไม่ได้ใช้ cache
  3. ครอบ render ด้วย try/catch: ถ้าพัง render ใหม่จาก cache ถ้ายังพังอีก render layout เดิมเป็นขีด "—" + ⚠ ไม่ปล่อยให้ widget ว่าง
  4. เก็บ log บนมือถือ 20 รอบล่าสุด (เวลา, แหล่งที่ใช้, เวลาที่ใช้ดึง ms, error) ใน `FileManager.local()` แล้วโชว์ในหน้า detail จะได้มีหลักฐานจริงในครั้งหน้า
- **ความเสี่ยง:** ต่ำ

### 2.5 % แดงค้าง ทั้งที่หน้าต่างรีเซ็ตแล้ว (Claude · Codex · AGY): **อันดับ 5**
- **อาการ:** แถบ % ยังแดง แต่ข้อความใต้แถบบอก "พร้อมใช้" หรือ "รีเซ็ตแล้ว"
- **สาเหตุ + หลักฐาน:**
  - `countdown()` รู้ว่ารีเซ็ตแล้ว (`Claude Usage.js:72`) แต่ `metricRow()` ยังใช้ `utilization` เดิม (`:131-138`)
  - ตัวอย่างจริง: ไฟล์ AGY ตอน 20:12Z บอก gemini weekly รีเซ็ต 20:39Z แต่ feed รอบถัดไปมาตอน 20:27Z และ 20:42Z ระหว่างนั้นข้อมูลขัดกันเอง
- **วิธีแก้ (ข้อมูลล้วน):** ถ้า `resets_at` ≤ ตอนนี้ ให้นับหน้าต่างนั้นเป็น 0% และเติม ⚠ ที่ป้ายเดิม จนกว่าข้อมูลรอบใหม่จะมา
- **ความเสี่ยง:** ต่ำ ระหว่างรีเซ็ตจนถึงรอบ feed ถัดไป (≤ 15 นาที) ตัวเลขอาจต่ำกว่าจริงนิดหน่อย มี ⚠ บอกไว้แล้ว

### 2.6 feed AGY/Codex เขียนไฟล์ไม่ atomic: **อันดับ 6 (เกิดยาก แต่เป็นตัวจุดชนวนข้อ 2.1)**

- **วิธีแก้:** เขียนลง tmp แล้ว `os.replace` ทำได้ เพราะ container mount ทั้งโฟลเดอร์ `/opt/usage` ไม่ได้ mount ไฟล์เดี่ยว (ตรวจแล้ว) การ rename จึงเห็นผลทันที
- **ความเสี่ยง:** ต่ำมาก

### 2.7 ตัวกัน token ตอน deploy (กฎข้อ 3 ของ repo): ตอนนี้ปกติ แต่มีจุดเสี่ยงซ่อนอยู่
- **ผลตรวจ:** deploy ทั้ง 5 ตัวใช้ sed แบบเจาะจง `s|k=__USAGE_TOKEN__|k=$TOK|` ✔ · ไฟล์ที่ deploy แล้วบน Mac มี placeholder เหลือตัวกัน 1 ตัวครบทั้ง 5 ไฟล์ ✔ · token ปัจจุบันเป็นตัวอักษรกับตัวเลขล้วน ✔
- **จุดเสี่ยง:**
  1. ตอน deploy ดึง token ซ้ำด้วย regex `[A-Za-z0-9]+` (`claude-usage/deploy.sh:24`, `codex-usage/deploy.sh:29`, RAM/Disk) ถ้าวันหนึ่งหมุน token ใหม่แล้วมี `-` หรือ `_` regex จะตัด token ให้สั้นลงแบบเงียบๆ → 401 ทุกครั้ง → widget ค้าง cache ตลอดไป
  2. `codex-usage/deploy.sh:37-39` ถ้าไม่เจอ token จะ deploy placeholder ทั้งอย่างนั้น (โหมดอ่าน iCloud ซึ่งตายไปแล้ว)
  3. sed ไม่ได้ escape `&` และ `|`
- **วิธีแก้:**
  1. deploy อ่าน `USAGE_TOKEN` จาก Infisical ผ่าน `infisical run` (ตามกฎ secrets ของ org) แทนการขูดจากไฟล์ที่ deploy แล้ว
  2. ตรวจ token ด้วย `^[A-Za-z0-9_-]{20,}$` และ escape ก่อนใส่ใน sed
  3. ไม่มี token = ไม่ deploy (เหมือน RAM/Disk)
  4. หลัง deploy ทุกตัวต้องได้ guard = 1 และเช็ค HTTP 200 (RAM/Disk ทำอยู่แล้ว ให้ Claude/Codex/AGY ทำด้วย)
  - ตอนนี้ token อยู่ใน `.env` 2 ไฟล์บน Contabo (`/opt/claude-usage-monitor/serve/`, `/opt/usage/`) ยังไม่ได้ย้ายเข้า Infisical **ไม่ได้เปิดอ่านไฟล์**
- **ความเสี่ยง:** ต่ำ แต่ต้องย้าย secret ไป Infisical ก่อน (ตามลำดับ migration ของ org)

### 2.8 iCloud เขียนทับไฟล์เดิม (กฎข้อ 5): ปกติ เหลือจุดเล็กหนึ่งจุด
- deploy ใช้ `sed … > ไฟล์` ซึ่งเป็นการเขียนทับ inode เดิม ✔
- แต่ Scriptable เติม header 3 บรรทัดลงไฟล์เองหลัง deploy (Claude/Codex/AGY) → มีคนเขียน 2 ฝั่งภายในไม่กี่วินาที → มีโอกาสเกิด iCloud conflict copy
- **วิธีแก้:** ใส่ header ไว้ใน source เลย (Disk Monitor ทำแบบนี้อยู่แล้ว) จะได้ไม่มีใครเขียนซ้ำ และ hash ก็เทียบกับ repo ได้ตรงๆ
- **ยังไม่ได้ตรวจ:** มีไฟล์ conflict copy (`* 2.js`) อยู่ในโฟลเดอร์ Scriptable หรือเปล่า

### 2.9 Server เดิมใช้ thread เดียว
- `serve.py` (claude/codex/agy) ใช้ `HTTPServer` → ถ้ามี client ช้าค้างอยู่ คนอื่นต้องรอ
- **วิธีแก้:** เปลี่ยนเป็น `ThreadingHTTPServer` (disk hub ใช้อยู่แล้ว) ความเสี่ยงต่ำมาก

### 2.10 ตัววัดที่ต้องมีก่อน จะได้มีเลขจริง
- **Server:** `serve.py` ทั้ง 3 ตัว log 1 บรรทัดต่อ request: เวลา, path, status, ms **ไม่เก็บ token ไม่เก็บ IP** → ได้อัตราที่มือถือดึงจริง (คือโควตา refresh ที่ iOS ให้จริง) และนับได้ว่าพลาดกี่ครั้ง
- **มือถือ:** log 20 รอบล่าสุดตามข้อ 2.4
- ใช้ข้อมูลนี้ทบทวนลำดับความถี่ในหัวข้อ 2 อีกครั้งหลังรันไปแล้ว 3 วัน
